# Pre-project study: documentation for LLMs + memory in Obsidian

> Date: **2026-09-23**. Four parallel web research passes, reading docs and source code, without installing or running anything. The most surprising claims were rechecked against primary sources.
> Status: **draft for decision**. No code has been written, and the choices are in [06-open-questions.md](06-open-questions.md).

> **Update 2026-09-23 (after the interview):** decisions take effect from [../OPEN-QUESTIONS.md](../OPEN-QUESTIONS.md) onward, and this study remains as a record of the research. These assumptions and proposals have been **superseded**:
> - Mandatory OneDrive → **optional OneDrive**, detected and confirmed during onboarding (`sync.provider`);
> - memory in a folder of the user's personal vault → **dedicated vaults**: one global and one per project;
> - per-device daily log → **only learnings and key points**, with templates;
> - project docs in the vault → **spec system (repository) ≠ memory system (vaults)**.

## TL;DR

**1. The community does have a way to document things so the LLM doesn't lose its way:** it's *Spec-Driven Development*, underpinned by *context engineering*. All approaches converge on 7 patterns:
1. short rules file (`AGENTS.md`);
2. interview before the spec;
3. short spec as source of truth;
4. open-questions log + ADRs;
5. plan broken into small tasks with checkboxes and a verification command;
6. state in a file + git + **a new session per phase**;
7. executable verification + hook-based gates.

→ [01](01-sdd-landscape.md)

**2. Ready-made toolkits that run on both pi AND Claude Code:**
- **Spec Kit:** the strictest about "ask and check before".
- **OpenSpec:** lightweight, with living specs.
- **Superpowers:** the best interview and TDD discipline.
- **BMAD:** comprehensive, but heavy.

Kiro, Agent OS, Task Master, and cc-sdd don't run on pi. → [02](02-comparison-and-evidence.md)

**3. The evidence calls for moderation:**
- A long `AGENTS.md`, or one generated by an LLM, **doesn't help** and costs more than 20% extra (ETH Zurich, 2026).
- A spec helps with **alignment and traceability**, not with finding more bugs (InfoQ, Sep/2026).
- Long plans don't get read (HumanLayer).

Short artifacts, reviewed early, and the code still gets read.

**4. About pi-hermes-memory** (v0.9.9, **MIT**, can be reused while keeping the copyright notices):
- In default mode, the 5,000-char limit **is no longer applied** to writes. The real limit is **what reaches the model**, because the search is lexical and tuned for English.
- **There is no storage layer** to swap out.
- Pointing the folder at the vault brings SQLite, locks, temp files, and hard links into OneDrive, which **is not recommended**.

→ [03](03-pi-hermes-memory-anatomy.md)

**5. Obsidian + OneDrive:**
- There's no ready-made solution. basic-memory is the closest one, but it's AGPL, so only the ideas can be reused.
- The way forward is **FS-first**: the vault holds **only Markdown**; index, locks, and config stay local.
- Risk #1 is **OneDrive placeholders**, which have already caused real data loss with agents. There are mitigations in code.

→ [04](04-obsidian-onedrive-memory.md)

**6. Proposal** (→ [05](05-reuse-proposal.md)):
- **Methodology ★:** OpenSpec + a project layer in `docs/` + our own question gate (`/interview` + `OPEN-QUESTIONS.md` + rules in `AGENTS.md`).
- **Project ★:** a new "Obsidian-first" package, reusing the scanner, prompts, review, flush, correction detection, and session search from pi-hermes-memory, and swapping the persistence layer for a `VaultBackend` that is safe for OneDrive, with `/memory-setup` and `/memory-doctor` onboarding.
